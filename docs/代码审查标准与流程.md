# 代码审查标准与流程（RAG 项目）

> 适用范围：RAG 通用多学科智能学习平台（Spring Boot + Spring AI 后端 / Vue3 + Element Plus 前端）。
> 本文档定义**审什么、怎么审、谁来审、何时算通过**，与 `项目规范.md`、`AGENTS.md` 衔接，可随团队从"单人自审"平滑升级为"多人 MR 互审"。
> 角色定位：**审查者是导师，不是守门员**——每条意见都要能教会作者一点东西。

---

## 1. 目标与原则

- **提升质量，而非挑刺**：审查聚焦正确性、安全性、可维护性、性能、测试覆盖，不纠结 tab/空格等可由 linter 处理的风格问题。
- **可落地**：清单条目对应本项目的真实风险点（RAG 链路、JWT、授权、文件上传、配额），而非泛泛而谈。
- **及早、小批量**：小变更随时审，大特性按分支拆分后审；一次 PR 建议不超过 ~400 行有效改动，便于深入而非走过场。
- **对事不对人**：用"这里可能……""建议考虑……"，不用"你这里错了"。

---

## 2. 适用范围与审查分级

| 模式 | 适用阶段 | 触发 | 审查人 |
|------|----------|------|--------|
| **单人自审**（当前） | 本地仓库、单人开发 | 每次向 `main` 合并前 / 每次提交前 | 作者本人按 §5 清单逐项过一遍 |
| **多人 MR 互审**（未来） | 转为协作、有远程仓库 | 临时分支合回 `main` 前必须发起 MR | 至少 1 名非作者的 Reviewer 通过 |

> 当前为单人毕设/本地仓库（见 `项目规范.md`）。**现在就按本清单做自审**，是为未来多人协作打基础；一旦接入远程，直接启用 §6.6 的 MR 流程即可，无需重写标准。

---

## 3. 角色与职责

- **作者（Author）**：保证编译/构建通过、关键路径有测试、PR 描述清楚；主动标注"自认为风险最高"的改动点，方便 Reviewer 聚焦。
- **审查者（Reviewer）**：按 §5 清单逐项核查，给出带严重级别与理由的评论；不代替作者改代码，但可建议具体改法。
- **维护者（Maintainer）**：掌握合并门禁（§6.5），对 🔴 阻塞项有一票否决权；负责定期审计（§8）。

## 4. 严重级别定义

| 标记 | 名称 | 含义 | 处置 |
|------|------|------|------|
| 🔴 | 阻塞 Blocker | 安全问题、数据丢失/损坏、越权、竞态、破坏 API 契约、关键路径缺错误处理 | **必须修复后才能合并** |
| 🟡 | 建议 Suggestion | 缺输入校验、命名/逻辑混乱、重要行为缺测试、性能隐患、明显重复代码 | 应修复；作者与 Reviewer 协商，可登记为 follow-up issue |
| 💭 | 提示 Nit | 风格不一致、小命名、文档缺口、可选改进方案 | 锦上添花，不阻塞合并 |

**评论格式（每条都要写"为什么"+"怎么改"）**

```
🔴 **安全：RAG 检索越权风险**
位置：ChatController.ask / ChatService
问题：用户 question 与 courseIds 传入检索，需确认 courseIds 隔离对所有检索路径生效。

为什么：若隔离缺失，用户可检索到非授权课程的知识库内容（越权读取）。

建议：核对 ChatService 中向量检索与关键词检索两路都按 courseIds 过滤；并在单测中构造"跨课程查询应被过滤"的用例。
```

## 5. 审查清单（核心）

> 打勾项为本项目重点。代码已具备的良好实践见 §附录 A；当前需重点关注的风险见 §附录 B。

### 5.1 安全与授权 🔴
- [ ] **认证/授权分层正确**：`AuthInterceptor` 仅做"是否登录 + 是否管理员"，**资源级归属权必须在 Service 层校验**（参考 `DocumentService` 调 `CourseAccessService.requireReadableResource/requireManagedResource`）。新增接口若直接读 `UserContext.userId()` 拼查询但未校验归属，判 🔴。
- [ ] **无越权读/写**：每个按 `id` 访问的资源（文档、问答记录、计划、帖子……）都必须确认"当前用户能否访问该 id"，不可仅信任前端传入的 id。
- [ ] **SQL 注入**：确认无 `${}` 字符串拼接、无 `Statement` 拼接；本项目 Mapper 统一用 MyBatis-Plus `QueryWrapper`，新增自定义 XML/SQL 时重点查 `${}` 与 `statementType=STATEMENT`。
- [ ] **JWT 安全**：`JwtUtil` 用 HS256，`Keys.hmacShaKeyFor` 要求密钥 ≥256 bit。**外部部署必须设置强 `JWT_SECRET`**（README 已强调）；不允许把默认密钥带上线。
- [ ] **文件上传**：白名单后缀、大小上限、存储用 UUID 重命名（防路径穿越）、不回显原始文件名到路径。**核查：`application.yml` 是否配置 `spring.servlet.multipart.max-file-size`**；当前 `DocumentService.upload` 未显式限制大小，判 🟡。
- [ ] **RAG 提示注入与防编造**：用户 `question` 会进入 LLM prompt。确认 system prompt 强制"仅依据召回片段、必须带 `[n]` 引用、不得编造"；且检索隔离（courseIds）生效。**这是本项目最高频风险，判 🔴 若缺失。**
- [ ] **配额 fail-open**：Redis 宕机时配额放行是毕设演示的有意取舍（README 八）；**外部正式部署应改为 fail-close**，审查相关改动时提示此权衡。
- [ ] **`?token=` 暴露**：仅预览类接口接受 URL token（浏览器内建 PDF 查看器限制）；确认主链路只用 Header，且 token 不进入业务日志。
- [ ] **日志脱敏**：不得记录明文 token、密码、`LLM_API_KEY`/`EMBED_API_KEY`、用户隐私。

### 5.2 输入校验与契约 🟡
- [ ] 对外接口入参有校验：`@Validated` + `@NotNull/@Min/@Max`、枚举/范围校验（如 `visibility` 0–2）。当前 `DocumentController` 参数多依赖 Service 内部兜底，建议 Controller 层也加约束，失败更早、报错更友好（🟡）。
- [ ] DTO 与响应结构稳定：新增/修改字段是否破坏前端契约；分页、错误码（`Result.code`）保持一致。
- [ ] 边界值：空集合、null、`Long` id 不存在时的行为是否符合预期（返回 404/空列表而非 500）。

### 5.3 RAG 核心正确性 🔴/🟡
- [ ] **检索隔离**：向量 + 关键词双路召回都按 `courseIds` 过滤；重排（Reranker）同样隔离。
- [ ] **引用溯源准确性**：回答中的 `[n]` 必须对应真实召回片段，且能在前端点击跳转/定位；不得出现"幽灵引用"。
- [ ] **降级逻辑**：关键词路无全文索引时降级为仅向量、重排未配置时关闭——确认这些降级不静默丢失关键信息。
- [ ] **分块与参数**：分块大小/重叠、Top-K、阈值变更有无回归；管理端可调参数是否做了合法范围校验。
- [ ] **防编造**：客观事实必须有出处；"知识库未覆盖"时应明确告知而非硬编。

### 5.4 错误处理与响应 🟡
- [ ] 统一出口：所有异常经 `GlobalExceptionHandler` 转 `Result`，**不向客户端泄露堆栈/SQL**；业务错误用 `BizException` 带明确中文消息。
- [ ] 关键路径（支付/考试/扣配额/删资源）失败有补偿或明确错误，不出现"半完成状态"。
- [ ] SSE 流式接口（`/api/chat/ask/stream`）有错误处理、超时与背压考虑，断流/异常时能正常结束。

### 5.5 并发与原子性 🔴
- [ ] 考试提交、配额扣减、状态机流转使用**原子更新/数据库约束**防重复提交与超卖（README 已说明考试重复交卷由原子状态更新阻止，审查相关改动须保留此保证）。
- [ ] 跨表操作在事务内（`@Transactional`），异常能回滚；注意自调用导致事务失效。
- [ ] Redis/外部服务不可用时不影响核心数据一致性，或 fail-close。

### 5.6 性能 🟡
- [ ] 无 N+1：批量查询走 `in`/联表，不在循环里查库。
- [ ] 嵌入/入库批量调用，避免逐条请求外部模型。
- [ ] 大文件/大文档解析有超时与内存控制；列表接口有分页或上限（参考 `QaRecord` 查询 `LIMIT 200`）。
- [ ] 前端大数据渲染（ECharts、长列表）有无虚拟滚动/分片。

### 5.7 测试 🟡
- [ ] 关键路径有测试：授权边界（越权拒绝）、RAG 检索隔离、考试提交原子性、文件上传校验、配额。
- [ ] 改动含新分支/异常路径时，补充对应用例；集成测试覆盖端到端核心流（上传→解析→问答→引用）。
- [ ] 编译/构建：`mvn -o test`（后端）、`npm run build`（前端）通过后才可合并（衔接 `项目规范.md` §1）。

### 5.8 代码规范与可维护性 💭
- [ ] 分层清晰：controller 薄、service 承载业务、mapper/entity 职责单一；不把业务逻辑塞进 controller 或 mapper。
- [ ] 命名自解释；复杂逻辑/业务约束有注释（尤其中文业务含义）。
- [ ] 提交信息遵循 Conventional Commits（`项目规范.md` §3），一次提交一件事。
- [ ] 破坏性操作（删库/删表/强推）遵循 `项目规范.md` 禁止项；无 `rm -rf`、无 `git push -f` 已合并提交。

### 5.9 依赖与配置 🟡
- [ ] 新增依赖有理由、版本锁定，无已知高危漏洞（`mvn dependency:check` / `npm audit`）。
- [ ] 密钥/超时/外部服务地址走环境变量（参考 README 环境变量表），不硬编码。
- [ ] 第三方调用（LLM/OCR/嵌入）有超时、重试与降级，不无限阻塞。

## 6. 审查流程

### 6.1 提交前（衔接 `项目规范.md` §1）
1. `git status` 确认无未提交改动残留。
2. 后端 `mvn -o compile` / 前端 `npm run build` 通过。
3. 作者按 §5 清单**自审一遍**，标记可疑点。

### 6.2 发起审查
- **单人自审**：在合并/提交前完成 §5 勾选，必要时写简短自查笔记。
- **多人 MR**（未来）：从最新 `main` 切临时分支 → 按 §1 提交 → 同步 `main`、解决冲突、自测通过 → 发起 MR，填写 PR 模板（见 `.github/PULL_REQUEST_TEMPLATE.md`）→ 指派 Reviewer。

### 6.3 审查执行
- Reviewer 拉取分支，**先读 PR 描述再读代码**，按 §5 逐项核查。
- 用 §4 的评论格式留意见；🔴 必须给出可操作的修复建议。
- 不追求"找问题数量"，追求"本次改动是否更安全、更正确、更易维护"。

### 6.4 处置与迭代
- 作者逐条回应：修复 / 解释为何不改 / 登记 follow-up。
- 🔴 未解决 = 不可合并；🟡 由双方协商，可转为后续 issue；💭 不阻塞。

### 6.5 合并门禁
合并回 `main` 必须满足：
1. 编译/构建/测试通过（衔接 `项目规范.md`）；
2. **0 个未解决的 🔴**；
3. （多人时）至少 1 个非作者 Approve；
4. 冲突已解决并重新自测；
5. 合并后及时删除临时分支（≤3 个工作日）。

### 6.6 单人 → 多人升级路径
当前本地仓库无远程，按 §6.1–6.5 自审即可。一旦接入远程协作：
- 启用 `develop` 集成分支 + MR 互审 + 线上回滚双人确认（见 `项目规范.md` 开头说明）；
- 把 §6.2 的 MR 模板与 §7 的 CI 门禁接上，自动化跑编译/测试/lint，减少人工重复劳动。

## 7. 自动化与工具建议

| 层 | 工具 | 作用 | 门禁建议 |
|----|------|------|----------|
| 后端格式 | Spotless / Checkstyle | 统一格式、基础规范 | 提交前/CI 自动格式化 |
| 后端质量 | PMD / SonarLint | 空指针、资源泄漏、坏味道 | 🟡 级别告警纳入审查 |
| 后端测试 | JUnit5 + Testcontainers + JaCoCo | 单元/集成测试、覆盖率 | 关键路径覆盖率门槛（如 ≥60%） |
| 前端格式 | ESLint + Prettier | 风格、潜在错误 | `npm run lint` 通过 |
| 前端测试 | Vitest + (Cypress) | 组件/关键交互 | 核心页面冒烟测试 |
| 流水线 | GitHub Actions（未来） | 自动跑 compile/test/lint/audit | 失败阻断合并 |

> 当前无 CI；建议先在本地把 `mvn -o test` 与 `npm run build` 固化为"合并前必跑"，再视协作需要上 CI。

## 8. 度量与持续改进

- **审查效率**：单次 PR 审查轮次、平均耗时（目标：小 PR ≤1 天）。
- **缺陷逃逸**：合并后在生产/演示中暴露、本应在审查发现的问题，回溯清单是否漏项。
- **定期审计**：每季度（或每个 release）抽样复盘 5–10 个历史 PR，更新 §5 清单，把反复出现的问题升级为 🔴 或自动化检查。
- **清单演进**：清单随技术栈与架构变化修订，修订记录写在本文件末尾。

## 附录 A：本项目已具备的良好实践（审查时应保留）

- ✅ **集中式授权**：`CourseAccessService` 统一收口资源归属校验，`DocumentService` 各方法均传入 `UserContext.userId()` 校验，模式一致。
- ✅ **安全文件上传**：`DocumentService.upload` 用 `UUID` 重命名、白名单后缀、空文件校验，无路径穿越。
- ✅ **输入校验示例**：`ChatController.ask/askStream` 用 `@Valid @RequestBody AskReq`，且 `listManagedCourseIds` 做知识库隔离。
- ✅ **归属校验**：`ChatController.toggleFavorite` 显式校验 `record.getUserId().equals(...)`。
- ✅ **低风险 SQL**：Mappers 全走 MyBatis-Plus `QueryWrapper`，未发现 `${}` 拼接。

## 附录 B：当前需重点关注的风险项（据代码观察，建议优先补强）

- 🔴 **RAG 提示注入 / 检索越权防护**：确认 `ChatService` system prompt 强制"依片段、带引用、不编造"且 courseIds 隔离贯穿全部检索路径。
- 🟡 **上传文件大小上限**：`DocumentService.upload` 未显式限制 `max-file-size`，建议配置并在边界单测。
- 🟡 **前端引用渲染 XSS**：核查 `frontend/src/utils/citations.js` 及回答渲染组件——若用 `v-html` 直接插入 RAG 文本/引用，需 DOMPurify 清洗或改文本插值。
- 🟡 **Controller 层入参校验**：`DocumentController` 多数参数依赖 Service 兜底，建议补 `@Validated` + 约束注解。
- 🟡 **配额 fail-open**：外部部署须改为 fail-close（见 README 八）。
