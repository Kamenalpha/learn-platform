## 步骤 1：混合检索 + BGE-Reranker 重排

### 现状（大白话）

现在问答检索只走一条路：把问题变成一串数字，去 Chroma 里找"数字最接近"的 5 段文字。问题是：学生问"**第 3 章**的**梯度下降**公式"这种带专有名词的问题时，专有名词的"字面匹配"比"意思相近"更管用，而现在的链路完全没有字面匹配能力。

### 方法选型（选什么、为什么）

**关键词召回：选 MySQL 全文索引（ngram），不选 Lucene/ES。**
- 理由：`doc_chunk` 表本来就存了每段的原文（`content` 字段，见 `entity/DocChunk.java`），MySQL 8.0 自带 ngram 分词（专门处理中文这种没有空格的文字），加一个索引就能用。**不引入任何新组件**，IngestService 入库链路一行都不用改。
- 落选原因：ES 太重（多运维一个服务，毕设规模用不上）；应用内 Lucene 需要自己维护索引同步，删块/重解析时要小心一致性问题，收益配不上复杂度。

**重排：选 SiliconFlow 托管 BGE-Reranker（HTTP API），不选本地部署。**
- 理由：嵌入模型已经走 SiliconFlow（`EMBED_API_KEY`），重排走同一家只需在现有 HTTP 客户端模式上加一个调用，**零新增基础设施**；bge-reranker-v2-m3 是该赛道的开源标杆，和报告里 QAnything"两阶段检索"的选型一致。
- 落选原因：本地跑 reranker 需要额外显式/大内存，Windows 开发机负担大，且和"AI 走云端 API"的项目约定（PROJECT_CONVENTIONS 第 3 节）不符。

**分数融合：选 RRF（倒数排名融合）。**
- 大白话：两个召回各排一个名次，RRF 就是"名次靠前的加分多"，只看名次不看原始分数。为什么：向量相似度和 BM25 分数的**量纲完全不同**（一个 0~1，一个 0~30），直接相加没有意义；RRF 免去调"权重该几比几"的坑，效果稳定，是 Elasticsearch/Dify 内置的标准做法。

### 具体做法

1. 给 `doc_chunk.content` 建 ngram 全文索引（新增 SQL 脚本，老库可执行）。
2. 新建一个统一的检索入口 `RetrievalService`：三段流水线 = 粗召回（MySQL 关键词 + Chroma 向量各取 top 20）→ RRF 融合排序 → 重排精筛（可选开关）取最终 Top-K。权限校验（`courseAccessService.canReadResource`）沿用现有逻辑，放在融合之后、重排之前。
3. `ChatService.prepare()` 里的 `vectorStore.similaritySearch(...)` 整段替换为调用 `RetrievalService`；`ExamService.generate()` 同样替换。**检索入口收敛到一个类**，以后再改检索策略只动一处。
4. 配置：`KbConfig`（Redis 配置，管理员后台可调）增加 `rerankEnabled`、`rerankTopN` 两项；新环境变量 `RERANK_API_KEY`（默认复用 EMBED_API_KEY）/`RERANK_MODEL`。

### 修改范围

| 动作 | 文件 |
|------|------|
| 新增 | `backend/src/main/java/com/rag/edu/service/rag/RetrievalService.java`（核心，约 200 行） |
| 新增 | `sql/upgrade_fulltext_index.sql` |
| 修改 | `backend/.../service/rag/ChatService.java`（prepare 方法改调 RetrievalService，删除内联检索代码） |
| 修改 | `backend/.../service/rag/ExamService.java`（同上） |
| 修改 | `backend/.../service/KbConfigService.java`、`backend/.../dto/KbDtos.java`（加 2 个配置项） |
| 修改 | `backend/.../config/RagProperties.java`（加 rerank 模型/地址配置） |
| 修改 | `backend/src/main/resources/application.yml`（新环境变量） |
| 修改 | `frontend/src/views/admin/` 下 RAG 参数页（加重排开关）；`frontend/src/api/index.js` |

### 会带来什么 + 怎么验证

- 带专有名词、页码、章节号的问题命中率明显提升；重排让 Top-K 里"最相关的段落"排名更准。
- 验证：单测通过；用同一批问题在改动前后对比回答（步骤 2 做完后可量化对比）；`mvn -o test` 全绿。
- **兜底设计必须写进代码**：重排 API 调用失败时降级为"只用融合结果"，不阻断问答（和现有 OCR 未配置则关闭的思路一致）。

## 步骤 2：管理端"检索测试"调试页

### 现状

管理员能改 Top-K 和阈值，但改完只能自己跑去提问碰运气——看不见"这次到底召回了哪 5 段、各多少分"。调参等于盲调。

### 方法选型

不新建独立服务，**直接在步骤 1 的 `RetrievalService` 上加一个"调试模式"**：同一个检索流水线，把每一阶段（关键词召回结果、向量召回结果、融合后名次、重排后分数）的中间结果都带出来返回给前端。为什么：调试页必须和真实问答走**同一条代码路径**，否则"调试页看着很好、实际问答两回事"——共用一个类天然保证一致。

### 具体做法

1. `RetrievalService` 增加返回"带中间结果"的方法（正常问答调精简版，不增加开销）。
2. 管理端新接口：输入问题 + 可临时覆盖的参数（topK/阈值/重排开关）→ 返回各阶段结果。
3. 前端表格展示：每块显示原文摘要、来源文档、页码、向量分、关键词分、融合名次、重排分。

### 修改范围

| 动作 | 文件 |
|------|------|
| 修改 | `backend/.../service/rag/RetrievalService.java`（调试模式返回结构） |
| 新增 | 管理端 controller 的 `/api/admin/rag/debug` 接口（放进现有 admin controller 即可） |
| 修改 | `backend/.../dto/KbDtos.java`（调试响应 DTO） |
| 新增 | `frontend/src/views/admin/RagDebug.vue`（页面主体是两个 el-table） |
| 修改 | 前端路由 + 管理端菜单 + `frontend/src/api/index.js` |

### 会带来什么 + 怎么验证

- 调参从盲调变成看数据调；论文第 6 章的检索对比实验（纯向量 vs 混合 vs +重排）直接用这个页面截图。
- 验证：管理员登录实测三组参数对比；普通用户访问该接口应 403（补一条越权测试，参照既有越权回归测试的做法）。

## 步骤 3：出题输出 JSON 结构化加固

### 现状

出题时把格式要求写进提示词，模型返回一坨文本，代码再用"找 `{` 和 `}` 的位置"硬抠出 JSON（`ExamPracticeService.parseJsonArray`/`extractJson`）。模型偶尔输出不规范文本就会抠失败，出题直接报错。

### 方法选型

**选 Spring AI 自带的结构化输出（`ChatClient.entity()`），不选"提示词里再强调一遍 JSON 格式"。**
- 理由：`.entity()` 会让框架在请求里自动附上 JSON Schema 约束（OpenAI 兼容接口的 `response_format` 能力），并把返回内容**自动反序列化成 Java 对象**，格式错了框架负责重试/报错，而不是我们手写正则去抠。这正是对比报告里 PageLM 验证过的正确姿势，而且是框架原生能力，代码量反而减少。
- 落选原因：继续手抠 JSON 治标不治本，模型换一代（DeepSeek → 通义）可能就抠不动。

### 具体做法

1. 定义出题结果 record：`List<GeneratedQuestion>`，字段=题干/题型/选项数组/答案/解析/难度——与现有 `QuestionDtos` 对齐（选项就是数组，本次提交已改好，正好衔接）。
2. `generate()` 里 `chatClient.prompt()...call().entity(new ParameterizedTypeReference<List<GeneratedQuestion>>(){})`，删除 `parseJsonArray`/`extractJson`/`serializeOptions(JsonNode)` 这套手写解析。
3. 提示词只保留"内容要求"（考什么、难度、出几道），格式要求全部交给框架。

### 修改范围

| 动作 | 文件 |
|------|------|
| 修改 | `backend/.../service/ExamPracticeService.java`（generate 方法主体 + 删除手写解析约 60 行） |
| 新增 | 出题结果 record（可放在 `QuestionDtos.java` 内） |
| 修改 | `backend/src/test/java/com/rag/edu/service/ExamPracticeServiceTest.java`（更新 mock） |

### 会带来什么 + 怎么验证

- 出题成功率趋近 100%；未来加新题型只需改一个 record 字段。
- 验证：单测 mock 返回，跑通"生成→入库→出卷"全流程；真实调用 DeepSeek 出 3 组题人工核对格式。

## 步骤 4：引用点击跳转 PDF 原文

### 现状

回答里的引用是 [1][2] 纯文本编号，想知道出处只能自己去翻文件。其实后端返回的 `Source` 已经带了 `docId`、`page`（页码）、`snippet`（原文片段），**数据全都有，只是前端没用起来**。

### 方法选型

**分两期，第一期选"浏览器原生跳页"，不选 PDF.js 自研高亮。**
- 第一期：点击引用 → 抽屉展示来源信息（文档名/页码/原文片段）+ "查看原文第 N 页"按钮，链接用 `文件URL#page=N`——浏览器自带的 PDF 阅读器原生支持锚点跳页，**一行前端代码都不用多写**。
- 第二期（可选）：换 PDF.js 渲染并在文本层高亮具体段落（Kotaemon 的做法）。为什么先不做：需要引入 PDF.js 依赖、处理文本层坐标映射，工作量一周起步；而第一期能覆盖 80% 的溯源需求（知道是哪份文档第几页+原文片段），先验证用户是否真的点。
- 落选（直接上 PDF.js）：演示效果更炫但风险高（PDF.js 与现有文件服务权限链路的集成未知），不符合"先小步拿结果"的节奏。

### 具体做法

1. 抽一个通用的 `CitationDrawer.vue` 组件（来源列表 + 跳转按钮）。
2. `Chat.vue` / `Assistant.vue` 把回答文本里的 `[n]` 渲染成可点击 chip，点击打开抽屉并定位到第 n 条来源。

### 修改范围

| 动作 | 文件 |
|------|------|
| 新增 | `frontend/src/components/CitationDrawer.vue` |
| 修改 | `frontend/src/views/Chat.vue`、`frontend/src/views/Assistant.vue`（引用渲染） |
| 后端 | **无需改动**（Source 字段已齐；若发现历史 qa_record 缺 snippet 再补） |

### 会带来什么 + 怎么验证

- "可溯源"从口号变成看得见的交互，答辩演示最抓眼球的点；为第二期 PDF.js 高亮探明真实使用率。
- 验证：PC/移动端各点一遍引用跳转；无页码的块（TXT/Word）降级为只展示片段不显示跳转按钮。

## 步骤 5：错题变式训练

### 方法选型

**变式题生成复用步骤 3 的结构化输出 + 现有判分链路，不新建独立流程。**
- 理由：变式题本质上就是"换题面的再出题"，出题、入库、判分、错题回收这条链路这次提交刚加固完（服务端限时/原子判分），直接复用零新概念；唯一的新东西是"生成变式题的提示词"（输入=错题+错误答案+知识点，输出=2~3 道同考点新题）。

### 具体做法

1. 错题详情处加"生成变式题"按钮 → 后端取该题 + 该生错误答案 + 解析 + 挂的知识点 → LLM 生成结构化变式题 → 自动建一张轻量练习卷（标记来源=变式训练）。
2. 作答走现有判分；新错题照常回收，形成"错→练→再错→再练"闭环。

### 修改范围

| 动作 | 文件 |
|------|------|
| 修改 | `backend/.../service/ExamPracticeService.java`（加 generateVariants 方法，变式来源标记） |
| 修改 | `backend/.../controller/ExamController.java`（1 个新接口） |
| 修改 | `frontend/src/views/Exam.vue`（错题本 tab 加按钮与作答入口）、`frontend/src/api/index.js` |
| 新增 | 单测：变式题生成的 mock 用例 |

### 会带来什么

错题本从"记录"升级为"训练"，对标讯飞"举一反三"（竞品验证过的刚需），且开源圈无同类实现；演示闭环完整度再上一档。

## 步骤 7：Docker 一键部署

### 方法选型

**扩充现有 docker-compose.yml + 给后端写一个多阶段 Dockerfile，不引入 K8s/脚本框架。**
- 理由：compose 文件已存在（MySQL+Redis+Chroma），缺的只是"建库自动化"和"后端本体"。MySQL 官方镜像原生支持把 SQL 脚本挂到 `/docker-entrypoint-initdb.d/` 自动执行——建库问题白送解决。多阶段构建（第一段 mvn 打包、第二段只留 JDK17+jar）是 Java 容器化的标准做法。

### 修改范围

## 步骤 8：成本配额执行

## 执行纪律（每步都适用）
